* Package Management

Emacs packages are provided by Nix (see [[file:flake.nix][=flake.nix=]] and [[file:nix/hm-module.nix][=nix/hm-module.nix=]]):
the flake builds Emacs with every package below on =load-path=, so =use-package=
forms carry no =:ensure= and install nothing at runtime. Built-in
features (=emacs=, =eglot=, =org=, =dired=, …) use =:ensure nil=. To add a
package, add it to the =withPackages= list in =flake.nix= and rebuild.

** Garbage collection

=early-init.el= raises =gc-cons-threshold= to 1GB for fast startup but never
lowers it again, so GC almost never runs and eventually fires as a long pause
(often mid-completion). =gcmh= keeps the threshold tiny while typing and large
while idle, moving collection out of interactive work.

#+begin_src emacs-lisp
(use-package gcmh
  :init
  (gcmh-mode 1)
  :custom
  (gcmh-high-cons-threshold (* 128 1024 1024)))
#+end_src

** Spacious padding

[[https://github.com/protesilaos/spacious-padding][=spacious-padding=]] owns the internal border, fringes and window dividers --
one place instead of the =default-frame-alist= entries this used to be spread
across.

=:left-fringe-width= / =:right-fringe-width= keep the previous asymmetry: wide
enough on the left for diff-hl's fringe bitmaps (GUI only; the terminal falls
back to margin indicators), minimal on the right. =:internal-border-width=
keeps the previous value; header line, tab and divider widths are left at
spacious-padding's own defaults.

=:mode-line-width= is 0 -- spacious-padding adds no box of its own to the mode
line at all. [[*Mode-line][Moody]]'s tabs/ribbons need the mode line free of
any box (its own README says a box "conflicts with Moody"), and
=my/apply-modus-variant= (see [[*Themes][Themes]]) already strips Modus
Themes' own box while keeping the background contrast Moody needs -- a
second, spacious-padding-added box here would reintroduce the same conflict
from a different source.

#+begin_src emacs-lisp
(use-package spacious-padding
  :custom
  (spacious-padding-widths
   '( :internal-border-width 18
      :left-fringe-width 8
      :right-fringe-width 1
      :mode-line-width 0))
  :config
  (spacious-padding-mode 1))
#+end_src

#+begin_src emacs-lisp
(use-package dired
  :ensure nil
  :custom
  (dired-dwim-target t)
  (dired-guess-shell-alist-user
   '(("\\.\\(png\\|jpe?g\\|tiff\\)" "feh" "xdg-open" "open")
     ("\\.\\(mp[34]\\|m4a\\|ogg\\|flac\\|webm\\|mkv\\)" "mpv" "xdg-open" "open")
     (".*" "open" "xdg-open")))
  (dired-kill-when-opening-new-dired-buffer t)
  :config
  (when (eq system-type 'darwin)
    (let ((gls (executable-find "gls")))
      (when gls
        (setopt insert-directory-program gls))))
  (setopt dired-listing-switches
          "-l --almost-all --human-readable --group-directories-first --no-group")
  (put 'dired-find-alternate-file 'disabled nil)
  (defun my/dired-find-file-reuse ()
    "Open a directory in place (reusing the dired buffer); open files normally.
`dired-kill-when-opening-new-dired-buffer' only reuses the buffer when it is
shown in fewer than two windows (the `(< (length (get-buffer-window-list)) 2)'
guard in `dired--find-possibly-alternative-file'); with the buffer in two or
more windows RET falls back to `find-file' and spawns a new buffer.  This
reuses unconditionally for directories via `find-alternate-file'."
    (interactive)
    (let ((file (dired-get-file-for-visit)))
      (if (file-directory-p file)
          (progn (set-buffer-modified-p nil)
                 (find-alternate-file file))
        (find-file file))))
  ;; evil-collection binds RET -> dired-find-file when it initialises, which
  ;; happens (on `evil-mode') after this :config's own `with-eval-after-load'
  ;; has run -- so it would clobber a rebind made here directly.  Install ours
  ;; from `dired-mode-hook', which runs when a dired buffer is created, i.e.
  ;; after evil-collection has set up `dired-mode-map', so ours wins.
  (defun my/dired-rebind-return ()
    (when (fboundp 'evil-collection-define-key)
      (evil-collection-define-key 'normal 'dired-mode-map
        (kbd "RET") 'my/dired-find-file-reuse)))
  (add-hook 'dired-mode-hook #'my/dired-rebind-return))
#+end_src

** Dirvish

[[https://github.com/alexluigit/dirvish][=dirvish=]] is a polished front-end for dired. =dirvish-override-dired-mode=
routes every dired entry point (=dired=, =dired-jump=, the =<leader> x= bindings)
through dirvish, inheriting the dired settings above (listing switches,
single-buffer navigation). =nerd-icons= is already installed, so it supplies the
file glyphs. Rich previews (images, PDF, video) want extra CLI tools on =PATH=
(e.g. =ffmpegthumbnailer=, =poppler=, =mediainfo=); text/directory previews work
without them.

=dirvish-side= is the file-tree sidebar (replaces neotree): a project-rooted
panel on the right, matching neotree's width. =dirvish-side-follow-mode= keeps it
pointed at the current file, and TAB (=dirvish-subtree-toggle=) expands
subdirectories inline for tree-like navigation. Bound to =<leader> e= (see the
keybindings section), which toggles it.

#+begin_src emacs-lisp
(use-package dirvish
  :hook ((after-init . dirvish-override-dired-mode)
         (after-init . dirvish-side-follow-mode))
  :commands (dirvish-side)
  :custom
  (dirvish-attributes '(nerd-icons file-size))
  (dirvish-side-width 50)
  (dirvish-side-attributes '(nerd-icons file-size))
  (dirvish-side-display-alist '((side . right) (slot . -1)))
  :config
  ;; The subtree nesting guides (`dirvish-subtree-prefix' = " │") are text
  ;; glyphs, so the global `line-spacing' (0.2) breaks them into disconnected
  ;; segments. Drop the extra spacing in dirvish/dired buffers so the bars
  ;; join up; prose/code buffers keep the global line-spacing.
  (defun my/dirvish-tighten-line-spacing ()
    (setq-local line-spacing 0))
  (add-hook 'dired-mode-hook #'my/dirvish-tighten-line-spacing))
#+end_src

** Themes

Auto-switches [[https://github.com/protesilaos/modus-themes][Modus Themes]] between Operandi Tinted (light) and Vivendi
Tinted (dark) following the system appearance. [[https://github.com/LionyxML/auto-dark-emacs][=auto-dark=]] provides the
detection cross-platform (D-Bus on Linux, =ns-system-appearance=/AppleScript/
=osascript= on macOS), so this works the same on Linux and Darwin, in GUI and
terminal frames. When no detection mechanism exists (e.g. a Linux TTY with no
D-Bus session bus) it falls back to a fixed dark variant rather than warning
at startup.

Modus Themes comes from GNU ELPA rather than the copy bundled with Emacs 30.2,
which is 4.4.0 -- a full major version behind the =5.3.0= this configuration
otherwise tracks. It arrives through the Nix package set like every other
package, so there is no =:ensure nil= here.

=modus-themes-load-theme= is used instead of a plain =load-theme=: it already
disables every other Modus variant before loading the new one (=load-theme=
stacks rather than replaces, so a lingering variant would leave faces neither
theme specifies showing through with the wrong colours), and it passes
=:no-confirm= to =load-theme= itself, so nothing needs to go in
=custom-safe-themes= for either variant to load without a prompt.

Modus Themes still boxes =mode-line=/=mode-line-active=/=mode-line-inactive=
when the display supports it, and unlike Tokyo Night it has no
user option to turn that off -- the box is stripped by hand instead, every
switch. [[*Mode-line][Moody]]'s tabs/ribbons draw the mode line's background
as the "outer" colour around an "inner" fill taken from =default='s background
(=moody-ribbon-background=, =moody-wrap=); a box around the mode line
interrupts that slant graphic at the exact edge where a tab/ribbon would sit
(the same reason [[*Spacious padding][Spacious padding]]'s own
=:mode-line-width= is 0 here). Stripping the box does not touch the
background itself -- Modus Themes already gives =mode-line-active=/
=mode-line-inactive= their own =bg-mode-line-active=/=bg-mode-line-inactive=,
distinct from =default='s =bg-main=, which is exactly the contrast Moody needs.

#+begin_src emacs-lisp
(use-package modus-themes
  :custom
  ;; Comments already carry the theme's own italic slant via this option (they
  ;; inherit `modus-themes-slant', which is part of the theme's own faces and
  ;; therefore survives every `load-theme'). `font-lock-keyword-face' and the
  ;; generic `italic' face are not covered by any Modus Themes option -- Modus
  ;; only offers *bold* keywords, via `modus-themes-bold-constructs', not
  ;; italic ones -- so those two still need the manual re-apply below.
  (modus-themes-italic-constructs t)
  :config
  (defun my/modus-variant-for (appearance)
    "Return the Modus Themes variant symbol for system APPEARANCE.
APPEARANCE is `light' or `dark'.  Pure: no side effects, so it can be
unit-tested without loading a theme."
    (if (eq appearance 'light) 'modus-operandi-tinted 'modus-vivendi-tinted))
  (defun my/apply-diff-hl-faces ()
    "Colour the diff-hl faces from the active Modus Themes variant.
Called on every variant switch (and when diff-hl loads) so the fringe/margin
indicators track Operandi/Vivendi instead of being pinned to one palette.
No-op until diff-hl has loaded and defined its faces: the initial variant is
applied by the auto-dark block at startup, before the `:defer'red diff-hl
package exists, and `set-face-attribute' on an undefined face errors.  The
diff-hl block re-invokes this once its deffaces have run."
    (when (facep 'diff-hl-change)
      (set-face-attribute 'diff-hl-change nil :background 'unspecified
                          :foreground (modus-themes-get-color-value 'fg-changed))
      (set-face-attribute 'diff-hl-delete nil :background 'unspecified
                          :foreground (modus-themes-get-color-value 'fg-removed))
      (set-face-attribute 'diff-hl-insert nil :background 'unspecified
                          :foreground (modus-themes-get-color-value 'fg-added))))
  (defun my/apply-fringe-face ()
    "Match `fringe' and `margin's backgrounds to `default's `bg-main'.
Modus Themes gives `fringe' its own colour, a shade apart from `bg-main' --
that reads fine at the window edge, but Flycheck's indicators sit in the
*margin*, immediately to the right of the fringe (see the Flycheck section),
where the two backgrounds abut and the seam between them is exactly where the
error/warning glyphs are read. Levelling both to `bg-main' here, not at top
level, keeps this from reading the palette before the theme is loaded -- see
`my/apply-font-faces's docstring for why that broke the first client frame of
a daemon.
`margin' is Emacs 31's own basic face for margin display strings (Modus
Themes colours it the same as `fringe', which is what caused the seam in the
first place); it is guarded by `facep' the same way `my/apply-diff-hl-faces'
guards diff-hl's faces, so this stays a no-op rather than an error on the
Emacs 30 `emacs-nox' the CI checks still build tests against."
    (set-face-attribute 'fringe nil
                        :background (modus-themes-get-color-value 'bg-main))
    (when (facep 'margin)
      (set-face-attribute 'margin nil
                          :background (modus-themes-get-color-value 'bg-main))))
  (defun my/apply-font-faces ()
    "Re-apply the font attributes `load-theme' strips.
Everything is Maple Mono NF now, so no face needs its own family: an
unspecified family falls through to `default' at render time.  Two things do
not survive a reload and must be re-applied from the appearance hook -- the
same reason `my/apply-diff-hl-faces' exists:

  * `default' is themed by Modus Themes (fg/bg), so re-specifying it strips
    the family, height and weight;
  * `italic' and keyword lose their *slant* entirely, so a light/dark switch
    (or auto-dark's startup re-apply) would drop italics everywhere.
    `font-lock-comment-face' is not in this list: it inherits Modus Themes'
    own `modus-themes-slant' face, so `modus-themes-italic-constructs' (set
    above) keeps it italic across reloads without any help from here."
    (set-face-attribute 'default nil :font "Maple Mono NF"
                        :height 140 :weight 'medium)
    (dolist (face '(italic font-lock-keyword-face))
      (set-face-attribute face nil :slant 'italic)))
  (defun my/apply-modus-variant (appearance)
    "Load the Modus Themes variant for system APPEARANCE (`light'/`dark').
`modus-themes-load-theme' disables every other Modus variant first, so there
is no lingering variant leaving faces it does not specify with the wrong
colours."
    (modus-themes-load-theme (my/modus-variant-for appearance))
    ;; See the box/Moody note above.
    (set-face-attribute 'mode-line-active nil :box 'unspecified)
    (set-face-attribute 'mode-line-inactive nil :box 'unspecified)
    (my/apply-diff-hl-faces)
    (my/apply-fringe-face)
    (my/apply-font-faces)))

(use-package doom-themes
  :custom
  (doom-themes-enable-bold t)
  (doom-themes-enable-italic t)
  :config
  (doom-themes-visual-bell-config)
  (doom-themes-treemacs-config)
  (doom-themes-org-config))

;; Drive the variant switch off the system appearance, cross-platform. auto-dark
;; detects light/dark (D-Bus on Linux, ns-system-appearance/AppleScript on
;; macOS) and runs the mode hooks; auto-dark must not load themes of its own
;; here (hence the nil theme vars), since `my/apply-modus-variant' also
;; has to re-run `my/apply-diff-hl-faces'/`my/apply-font-faces' on every switch.
;;
;; `auto-dark-allow-osascript' lets macOS detect appearance via the `osascript'
;; binary, which works in a terminal frame too (the AppleScript branch requires
;; a GUI `window-system', so `emacs -nw' would otherwise fall through).
;;
;; Some hosts have no detection mechanism at all (a Linux TTY/SSH session with
;; no D-Bus session bus). There `auto-dark-mode' would log "Could not determine
;; a viable theme detection mechanism!" at startup. `my/auto-dark-detectable-p'
;; mirrors auto-dark's own detection conditions without that warning side effect,
;; so we only enable the mode when it can work; otherwise we apply a fixed dark
;; variant and stay quiet.
(use-package auto-dark
  :after modus-themes
  :custom
  (auto-dark-dark-theme nil)
  (auto-dark-light-theme nil)
  (auto-dark-allow-osascript t)
  :config
  (defun my/auto-dark-detectable-p ()
    "Non-nil when a system-appearance detection method is available.
Mirrors `auto-dark--determine-detection-method' without its warning
side effect, so we can decide whether to enable `auto-dark-mode'."
    (cond
     ((eq system-type 'darwin)
      (or (memq window-system '(ns mac))              ; GUI -> applescript
          (and (bound-and-true-p auto-dark-allow-osascript)
               (executable-find "osascript"))))       ; terminal -> osascript
     ((eq system-type 'gnu/linux)
      (and (featurep 'dbus)
           (ignore-errors                             ; no session bus -> error
             (member "org.freedesktop.portal.Desktop"
                     (dbus-list-activatable-names :session)))))
     ((eq system-type 'windows-nt) t)
     (t nil)))
  (add-hook 'auto-dark-dark-mode-hook
            (lambda () (my/apply-modus-variant 'dark)))
  (add-hook 'auto-dark-light-mode-hook
            (lambda () (my/apply-modus-variant 'light)))
  (if (my/auto-dark-detectable-p)
      (auto-dark-mode)
    ;; No detectable mechanism (e.g. Linux TTY/SSH). Skip the mode and its
    ;; startup warning; apply a fixed dark variant instead.
    (my/apply-modus-variant 'dark)))
#+end_src

;; Inter was chosen on x-height -- 0.546em against Maple Mono's 0.550em -- so both
;; look the same size at one `:height' and prose needs no fudge factor. Its static
;; instances use typographic families (`Inter Medium' carries nameID 16 `Inter'),
;; so the family plus `:weight' resolves without naming a per-weight family.
(set-face-attribute 'variable-pitch nil
                    :font "Inter"
                    :height 140
                    :weight 'medium)
(set-face-attribute 'fixed-pitch nil
                    :font "Maple Mono NF"
                    :height 140
                    :weight 'medium)

;; face inherited by org/markdown emphasis; font-lock-comment/keyword-face slant
;; themselves directly. These are all restyled on every `load-theme', so they
;; are applied in `my/apply-font-faces' (called from the appearance hook)

(add-to-list 'default-frame-alist '(ns-transparent-titlebar . t))
(add-to-list 'default-frame-alist '(ns-appearance . dark))

;; The fringe's own colour (a shade apart from `default's `bg-main') left a
;; visible seam right where Flycheck's margin indicators sit, just inside it --
;; `my/apply-fringe-face' (called from the appearance hook, alongside
;; `my/apply-diff-hl-faces') levels it to `bg-main' instead. That is not done
;; here at top level: reading the palette this way once, at *load* time, is
;; before the theme has been applied and, in a daemon, before any frame exists --
;; the first client frame got a mis-coloured fringe that only corrected itself

;; fixes level-3 headings.
;;
;; `set-fontset-font' only exists in a window-system build, and this is top
;; level: unguarded, it aborts the load of the whole rest of config.el on the

;; `fboundp' rather than `display-graphic-p' so a GUI-capable Emacs started with

(when (fboundp 'set-fontset-font)

** Ligatures

Maple Mono ships the same Fira Code/Cascadia-style ligature set (arrows,
comparisons, punctuation runs) via its `calt' table, which is meant to draw
each ligature as independent partial glyphs with nothing composed -- but that
did not render here in practice. =ligature.el= composes the pair explicitly
instead. It works by rewriting =composition-function-table=, which is plain
character-table manipulation with no window-system dependency, so it is
harmless (just invisible) on a terminal-only build.

#+begin_src emacs-lisp
(use-package ligature
  :config
  ;; The standard Cascadia Code / Fira Code superset from ligature.el's own
  ;; README. Emacs skips whichever glyphs the active font does not shape, so
  ;; listing more than Maple Mono supports is harmless.
  (ligature-set-ligatures 'prog-mode

* Tree-sitter

=global-treesit-auto-mode= advises =set-auto-mode-0= to rebuild
=major-mode-remap-alist= from scratch on /every/ file opened --
=treesit-auto--build-major-mode-remap-alist= calls =treesit-language-available-p=
once per known recipe (around 190 checks), each a filesystem probe for that
language's shared library. That is the single biggest cost in opening any file
here: profiling a plain file open showed ~0.9s of a ~1.1s =normal-mode= inside
this one rebuild. Once the OS page cache is warm for those ~190 shared
libraries the probes are cheap, which is why the delay seemed to go away after
the first file or two -- but it comes straight back for the first file opened
after a restart, which is exactly what "switch to a project, then open a file"
usually is.

The grammars on disk barely change once installed, so the fix is a cache:
build the remap alist once, eagerly, right here at startup rather than
lazily on the first file, so the one-time cost lands during Emacs' own
startup instead of during a later interactive file open. It only needs
rebuilding when =treesit-auto--maybe-install-grammar= is about to actually
attempt an install (i.e. the recipe is not yet ready) -- not every time it
merely runs, which is on every file whose language it already recognises.

#+begin_src emacs-lisp
(use-package treesit-auto
  :custom
  (treesit-auto-install 'prompt)
  :config
  (treesit-auto-add-to-auto-mode-alist 'all)
  (global-treesit-auto-mode t)

  (defvar my/treesit-auto-remap-alist-cache nil
    "Cached result of `treesit-auto--build-major-mode-remap-alist'.
`global-treesit-auto-mode' rebuilds that alist -- one
`treesit-language-available-p' filesystem probe per known recipe -- on every
file opened, which costs the better part of a second even though the answer
does not change between one file and the next.")

  (advice-add #'treesit-auto--build-major-mode-remap-alist :around
              (lambda (orig &rest args)
                (or my/treesit-auto-remap-alist-cache
                    (setq my/treesit-auto-remap-alist-cache (apply orig args)))))

  ;; Only invalidate when a grammar recipe is not yet ready, i.e. right
  ;; before `treesit-auto--maybe-install-grammar' might actually install one
  ;; -- not on every call, which happens on every file whose language is
  ;; already installed and would otherwise throw the cache away each time.
  (advice-add #'treesit-auto--maybe-install-grammar :before
              (lambda (&rest _)
                (when-let* ((recipe (treesit-auto--get-mode-recipe))
                            (ts-mode (treesit-auto-recipe-ts-mode recipe))
                            ((not (treesit-auto--ready-p ts-mode))))
                  (setq my/treesit-auto-remap-alist-cache nil))))

  ;; Prime the cache now, during startup, rather than paying for it on
  ;; whichever file happens to be opened first.
  (setq my/treesit-auto-remap-alist-cache
        (treesit-auto--build-major-mode-remap-alist)))
#+end_src

* Mode-line

[[https://github.com/tarsius/moody][=moody=]] does not replace the mode line the way =mood-line= (previously used
here) did -- it only restyles a couple of built-in elements
(=mode-line-buffer-identification=, =vc-mode=) as tab/ribbon shapes, via
=moody-replace-mode-line-buffer-identification= and =moody-replace-vc-mode=.
Everything else is a hand-built =mode-line-format=, built from stock Emacs and
Flycheck constructs rather than mood-line's custom segments, so those two
=moody-replace-*= calls have the exact elements they expect to find and
substitute:

- =mode-line-buffer-identification= and =(vc-mode vc-mode)= are included
  verbatim -- =moody-replace-*= finds and replaces those exact sub-forms in
  =mode-line-format= (=cl-subst= with an =equal= test), so they have to appear
  as themselves, not pre-wrapped in anything.
- =mode-line-format-right-align= (Emacs 30+) replaces the manual padding
  math mood-line did internally to right-align its second half.
- The Evil tag comes from =evil-generate-mode-line-tag= called directly,
  rather than through =evil-mode-line-tag=/=evil-mode-line-format=: Evil
  auto-inserts/removes that symbol from =mode-line-format= itself on every
  state change, hunting for an anchor element (=mode-line-position= by
  default) to insert around, which is one more moving part than a plain
  =:eval= needs.
- Flycheck's own =flycheck-mode-line= construct (its =:lighter=, normally only
  seen via =minor-mode-alist=) stands in for mood-line's checker segment --
  already colour-coded per severity, no custom hooks required.

Moody draws its tab/ribbon slants as tiny XPM images built from three raw
colour values. On macOS, Emacs' NS port does not interpret those the way
X11/other platforms do -- colours come out wrong (a washed-out patch behind
the slant, unrelated to any face) unless converted through a colour-space
correction first; =moody-slant= (the default) is correct everywhere else,
hence the platform guard.

Moody's own correction, =moody-slant-apple-rgb=, pre-compensates every slant
colour by decoding it with a 1.8 gamma (chasing a legacy "Apple RGB" profile
NS is assumed to reinterpret raw image pixels through) before handing it to
`create-image'. On this build that over-corrects slightly: every slant
colour comes out a touch darker than the face it is supposed to match,
visible as the mode-line-adjacent half of the buffer-identification/vc-mode
glyphs reading darker than =mode-line-active=/=mode-line-inactive= right next
to them. Reworking the exponent into `color-srgb-to-xyz' plus the same
inverse matrix shows *why*: decoding with a gamma of ~2.2 instead very nearly
reconstructs the original colour (i.e. cancels the correction outright,
which is exactly the washed-out failure mode the correction exists to avoid)
-- so the true value NS needs sits somewhere between 1.8 and that, not at
either end. =my/moody-slant-srgb= is the same conversion with the exponent
pulled out into =my/moody-slant-gamma= so it can be tuned in one place
without re-deriving the maths -- currently 2.1, after an initial 2.0 (still
reported as slightly dark) nudged one step further from 1.8; everything else
-- the sRGB -> XYZ step, the inverse matrix, `moody-slant' underneath -- is
untouched. This has not been verified against a real display from here;
if 2.0 is still off, nudge =my/moody-slant-gamma= up (lighter) or down
(darker) a step at a time.

Both tabs and ribbons fill their *inside* (as opposed to the slant itself)
from =default='s background -- =bg-main=, the same colour the buffer itself
uses. That is Moody's own design, not something this config adds: the fill is
meant to read as a piece of the buffer poking up into the bar, distinct from
=mode-line-active='s/=mode-line-inactive='s own background by design (the
whole reason a slant is worth drawing at all -- see the box/Moody note
above). In Modus Vivendi Tinted =bg-main= (near-black) is a lot darker than
=bg-mode-line-active= (a mid grey-blue), so the contrast is more pronounced
than in most themes, but it is not a bug to fix -- softening or removing it
was tried twice (recoloured =moody-ribbon-background= to a dedicated,
in-between shade; matched it to the mode line exactly) and both attempts made
it look worse: matching it exactly leaves the slant image with no contrast to
draw at all, so the tab/ribbon silhouette disappears; anything in between
still reads as an arbitrary, slightly-off colour rather than an intentional
one. The stock two-tone look is the one that reads as deliberate.

One real bug did come out of that detour, worth keeping in mind if this is
revisited: rebuilding buffer identification from =moody-ribbon= instead of
=moody-tab= (to make it consult =moody-ribbon-background= at all -- =moody-tab=
never does, its fill is hard-coded to =default=) changes more than the fill
colour. =moody-wrap='s tab/ribbon =pcase= draws the *right-hand* glyph with a
different direction and colour order depending on =type= (see the source), so
switching types mirrors that glyph -- the slant angles the wrong way relative
to the left-hand one, breaking the tab illusion outright. Any future attempt
to retarget the fill has to preserve =type= as-is (=moody-tab= for buffer
identification, =moody-ribbon= for =vc-mode=) and change the colour at its
actual source -- advising =moody-wrap= itself, since =inner= is a local
binding inside one large =let*=, not something a =:filter-*=/=:around= advice
could reach without re-deriving it anyway -- rather than switching which
function builds the element.

#+begin_src emacs-lisp
(defun my/mode-line-evil-tag ()
  "Return the current Evil state tag (e.g. <N>, <I>), or nil outside Evil."
  (when (bound-and-true-p evil-local-mode)
    (evil-generate-mode-line-tag evil-state)))

(defun my/mode-line-buffer-status ()
  "Modified/read-only indicator for the current buffer."
  (cond
   ((buffer-modified-p) (propertize "●" 'face 'error))
   (buffer-read-only (propertize "■" 'face 'shadow))
   (t " ")))

(setopt mode-line-format
        '("%e"
          (:eval (my/mode-line-evil-tag)) " "
          (:eval (my/mode-line-buffer-status)) " "
          mode-line-buffer-identification
          "  " mode-line-position
          mode-line-format-right-align
          (vc-mode vc-mode) "  "
          (:eval (propertize (format-mode-line mode-name) 'face 'bold)) "  "

(use-package moody
  :config
  (defvar my/moody-slant-gamma 2.1
    "Gamma this build's NS port needs to decode Moody's slant colours correctly.
See the Mode-line prose above: `moody-slant-apple-rgb' uses a fixed 1.8 and
over-corrects here (every slant colour comes out too dark); 2.2 turns out to
cancel the correction outright (reproducing the washed-out colours the
correction exists to avoid), so the right value is somewhere between the two
and has to be found empirically. Adjust this one number to retune
`my/moody-slant-srgb' without re-deriving the maths.")
  (defun my/moody-slant-srgb (direction c1 c2 c3 &optional height)
    "Like `moody-slant-apple-rgb', but decoded with `my/moody-slant-gamma'.
Same conversion otherwise: sRGB -> XYZ via `color-srgb-to-xyz', the same
inverse matrix back to linear RGB, `moody-slant' underneath."
    (require 'color)
    (cl-flet ((cnv (color)
                (pcase-let*
                    ((`(,r ,g ,b) (color-name-to-rgb color))
                     (`(,x ,y ,z) (color-srgb-to-xyz r g b))
                     (r (expt (+ (*  3.2404542 x)
                                 (* -1.5371385 y)
                                 (* -0.4985314 z))
                              (/ my/moody-slant-gamma)))
                     (g (expt (+ (* -0.9692660 x)
                                 (*  1.8760108 y)
                                 (*  0.0415560 z))
                              (/ my/moody-slant-gamma)))
                     (b (expt (+ (*  0.0556434 x)
                                 (* -0.2040259 y)
                                 (*  1.0572252 z))
                              (/ my/moody-slant-gamma))))
                  (color-rgb-to-hex r g b))))
      (moody-slant direction (cnv c1) (cnv c2) (cnv c3) height)))
  (when *is-a-mac*
    (setopt moody-slant-function #'my/moody-slant-srgb))
  (moody-replace-mode-line-buffer-identification)
  (moody-replace-vc-mode))
#+end_src

** Spelling (jinx)

=jinx= checks only the parts of a buffer that are prose, using the major mode's
own faces, so it stays quiet in code even inside comments-heavy files. It is
enabled per prose mode rather than globally: spell-checking every code buffer is
noise, and the value is in Org, Markdown, the [[*Notes (zk4e)][notes]] and commit
messages.

It talks to =libenchant=, which chooses a backend at runtime. On macOS nixpkgs'
enchant ships =enchant_applespell.so=, so the system dictionary is used with
nothing further installed -- =enchant-lsmod-2 -list-dicts= reports =de_DE=,
=en_AU=, =en_CA=, =en_GB= and =en_US= from AppleSpell.

=en_NZ=, and AppleSpell offers no such dictionary -- jinx then warns "No
dictionaries available" once and silently checks nothing. =en_GB= is the closest
available and takes NZ spelling: =colour= and =organisation= both pass, while
=sentance= and =mispelled= are caught. On Linux this instead wants a hunspell
dictionary (e.g. =hunspellDicts.en_GB-ise=) copied into
=$XDG_CONFIG_HOME/enchant/hunspell=; =DICPATH= is hunspell's own variable and
enchant ignores it.

** Markdown

=markdown-ts-mode= is Emacs 31's built-in tree-sitter Markdown mode. Once its
grammars are installed, [[*Tree-sitter][=treesit-auto=]] remaps =.md= buffers to
it automatically (its recipe covers the =markdown-mode= -> =markdown-ts-mode=
swap the same way it does for JS/TS), falling back to =markdown-mode= itself
when the grammars are absent -- e.g. =pkgs.emacs-nox= (Emacs 30.2) in CI, which
predates =markdown-ts-mode= entirely.

Unlike other built-in tree-sitter modes, =markdown-ts-mode= ships with no
autoload -- its own commentary calls it experimental and says Emacs does not
yet enable it by default. =treesit-auto= only ever checks =fboundp= on a
recipe's ts-mode; it never ~require~s one itself, so without a =require=
somewhere =markdown-ts-mode= would stay void and =treesit-auto= would never
remap to it. Hence the ~require~ in =:init= below, which runs unconditionally
at startup (well before =treesit-auto= builds its remap alist on the first
file visit), guarded with =noerror= so Emacs 30.2 silently no-ops instead of
erroring.

=markdown-mode= (the package) stays regardless -- it is =treesit-auto='s
fallback when the grammars are missing, and it is also where
=markdown-command=/=markdown-do= live, neither of which =markdown-ts-mode=
replaces. =C-c C-e= is therefore bound on both keymaps.

#+begin_src emacs-lisp
(use-package markdown-mode
  :defer t
  :init
  (setopt markdown-command "multimarkdown")
  (require 'markdown-ts-mode nil t)
  :bind (:map markdown-mode-map
              ("C-c C-e" . markdown-do))
  :config
  (when (fboundp 'markdown-ts-mode)
    (define-key markdown-ts-mode-map (kbd "C-c C-e") #'markdown-do)))
#+end_src

** Nix

Eglot needs no =eglot-server-programs= entry here: it already maps =nix-mode= to
an =eglot-alternatives= list of =nil=, =rnix-lsp= and =nixd=, and picks the first
of those on =PATH=. The closure supplies
[[https://github.com/nix-community/nixd][=nixd=]] and no =nil=, so =nixd= is what
gets used.

=nixd= /evaluates/ Nix rather than only parsing it, which is what lets it
complete attribute paths and option names. That needs an expression to evaluate
against, which nixd reads from a project [[file:.nixd.json][=.nixd.json=]] --
per-project, so not configured here. This repo's points =nixpkgs.expr= at its own
flake input, so package names complete inside =emacsToolsFor= and
=dotemacsPackageList=:

#+begin_example
{ "nixpkgs": { "expr": "import (builtins.getFlake \"…/dotemacs.d\").inputs.nixpkgs { }" } }
#+end_example

A configuration repo wants =options= providers too, keyed by name, each an
/options attrset/ rather than a module -- e.g.
=darwinConfigurations.<host>.options= for nix-darwin, and
=.options.home-manager.users.type.getSubOptions [ ]= for the home-manager options
nested inside it. The schema is =nixpkgs.expr=, =options.<name>.expr=,
=formatting.command= and =diagnostic.suppress=; =formatting= already defaults to
=nixfmt=, and [[*Formatting (Apheleia)][Apheleia]] owns formatting here anyway.

Formatting is [[https://github.com/NixOS/nixfmt][=nixfmt=]], reached through
[[*Formatting (Apheleia)][Apheleia]], which already ships
=(nixfmt . ("nixfmt"))= and maps both =nix-mode= and =nix-ts-mode= to it -- so
only the binary is needed. It is the same =nixfmt 1.4.0= that =nix fmt=
(nixfmt-tree) uses, so format-on-save and the pre-commit hook agree.

* Diagnostics (Flycheck)

Flycheck 38 in place of built-in Flymake. Eglot's diagnostics arrive through

=flycheck-eglot= package and clashes with it, so that package stays out of the

other line -- and machine-applicable fixes are a =C-c ! f= away, including
[[*ESLint][ESLint]]'s.

chain: it ran as =javascript-eslint= alongside Eglot. It is now a server behind
the [[*Eglot][=rass= multiplexer]], so a chain would report each ESLint result
twice -- once from the LSP diagnostics and once from the CLI checker. Flycheck
still reaches the checker in a buffer Eglot does not manage, because the
=eglot-check= predicate requires =eglot-managed-p=. See [[*ESLint][ESLint]].

Indicators go in the left margin -- the =auto= default draws them in the fringe,
which [[*Version Control (diff-hl)][diff-hl]] owns here; Flycheck widens the
margin by a column on its own.

levels, so the per-level nerd-font glyphs are written straight into each level's
margin spec -- the exact property =flycheck-error-level-margin-spec= reads --
which leaves every other property of the standard levels alone. Flycheck defines
the levels when it loads, so =:config= is late enough for this to stick. The
glyphs are single-column: Flycheck provisions a one-column margin, which would
clip the trailing space the Flymake indicators used to carry.

* Version Control (diff-hl)

=global-diff-hl-mode= is a /globalized/ minor mode: each enable walks
=buffer-list= and turns =diff-hl-mode= on in every buffer. Enabling it from a
=find-file= hook therefore repeated that walk for every file opened, over a
buffer list that [[*Consult][Consult]]'s previews keep making longer -- so
scrolling a long result list got slower as it went. The hook stays the trigger,
so the package still loads late rather than at startup, but the setup takes
itself off =find-file-hook= after the first file.

=diff-hl-flydiff-mode= is what shows indicators for /unsaved/ edits. It works by
advice: =diff-hl-changes-buffer= is overridden so the reference blob is extracted
to a temp file with =git cat-file= and the external =diff-program= runs against
the live buffer, rather than one =git diff= on the file as saved. A global idle
timer then re-runs that. It skips a buffer whose =buffer-chars-modified-tick= has
not moved, so an untouched buffer is never re-diffed -- the cost lands while you
type, which is why =diff-hl-flydiff-delay= is raised to 1s.

#+begin_src emacs-lisp
(defun my/diff-hl-setup ()
  "Turn the diff-hl global modes on once, then take this off `find-file-hook'.

run for every file opened, which repeated that walk over a buffer list
that Consult's previews keep making longer.  The hook is still the
trigger, so the package stays deferred until the first file, but one run
is enough."
  (remove-hook 'find-file-hook #'my/diff-hl-setup)
  (global-diff-hl-mode)
  (diff-hl-flydiff-mode)
  ;; GUI uses the graphical fringe bitmaps (need a left fringe -- see Spacious
  ;; padding). Only the terminal, which has no fringe, falls back to the text
  ;; margin indicators.
  (unless (display-graphic-p)

** Roslyn pull diagnostics

Roslyn reports diagnostics by /pull/ only. Driving =roslyn-ls= 5.10.0 over stdio,
with a project open and a file that has a real compile error, shows all three
halves of the problem:

- it sends no =textDocument/publishDiagnostics= at all, even after
  =workspace/projectInitializationComplete=;
- its initialize response has =diagnosticProvider: null=. It registers
  =textDocument/diagnostic= afterwards, with =client/registerCapability=;
- it answers a =textDocument/diagnostic= request with =kind: "full"= and the
  expected items (=CS0029=, =CS1002=, ...).

Eglot pulls diagnostics from 1.20, but chooses to by asking
=(eglot-server-capable :diagnosticProvider)=, and =eglot-server-capable= reads
only the initialize response. Eglot acts on exactly one dynamic registration,
=workspace/didChangeWatchedFiles=; every other registration reaches the default
method, which warns and does nothing. So Eglot never asks, Roslyn never
volunteers, and Flycheck's =eglot-check= correctly reports the nothing that Eglot
holds.

Writing the capability in when Roslyn registers it is enough to make Eglot's own
pull path (=eglot--flymake-pull=) run; it carries only =:textDocument= and an
optional =:previousResultId=, so the registration options themselves are never
read and any non-nil value will do. This reaches into Eglot internals -- =eglot--capabilities= is an
EIEIO accessor, and =eglot-register-capability= is an internal generic -- so it
is the most upgrade-fragile part of this configuration. The decision is kept in a
pure function so the merge is unit-tested; only the =setf= is uncovered.

#+begin_src emacs-lisp
(defun my/eglot-capabilities-with-pull-diagnostics (caps params)
  "Return CAPS with `:diagnosticProvider' set from registration PARAMS.
PARAMS is the `registerOptions' plist of a `textDocument/diagnostic' dynamic
registration, and may be nil.  Eglot only tests this value for truth: its pull
request carries `:textDocument' plus an optional `:previousResultId' and reads
none of the options, so nil PARAMS becomes t.
Pure: copies CAPS rather than writing through to the server's own plist."
  (plist-put (copy-sequence caps) :diagnosticProvider (or params t)))

(cl-defmethod eglot-register-capability
  (server (_method (eql textDocument/diagnostic)) _id &rest params)
  "Record Roslyn's dynamically registered pull diagnostics on SERVER.
Without this the registration hits Eglot's default method, which only warns,
and `eglot-server-capable' keeps reporting the null `diagnosticProvider' from
the initialize response."
  (setf (eglot--capabilities server)
        (my/eglot-capabilities-with-pull-diagnostics
         (eglot--capabilities server) params)))
#+end_src

That gets the diagnostics as far as Flycheck, where a second problem eats them.
Flycheck 38.3's bridge drops Eglot's =:region= argument:

#+begin_example
(defun flycheck-eglot--report (diags &rest _)
  (setq flycheck-eglot--diagnostics (append diags nil))
  ...)
#+end_example

Eglot reports nil with a /degenerate/ region -- =:region (POS . POS)= -- to mean
"keep what you have", and reports the whole buffer -- =(POINT-MIN . POINT-MAX)=
-- for a real update. It sends the first whenever a pull answers =unchanged=.
Roslyn answers =unchanged= for the second pull of an unedited buffer, and
Flycheck itself makes that second pull, because the first report triggers a
re-check. So the diagnostics arrive and are wiped about a second later:

#+begin_example
PULL id=99  kind=full      items=3
PULL id=100 kind=unchanged items=0    <- reported as nil, cache cleared
#+end_example

The advice restores the meaning of =:stay=. Eglot also uses =:stay= to fold
/pushed/ diagnostics in beside pulled ones, so a =:stay= carrying diagnostics
adds to the cache rather than replacing it. This is a Flycheck bug and affects
every pull server, not only Roslyn.

#+begin_src emacs-lisp
(defun my/flycheck-eglot-report-honour-stay (orig diags &rest args)
  "Treat Eglot's `:stay' reports as \"keep what you have\".
ORIG is `flycheck-eglot--report', which ignores the `:region' in ARGS and so
lets a nil DIAGS clear the buffer.  A degenerate region marks a `:stay'.
Known limit: in an empty buffer `point-min' equals `point-max', so a real
`:clear' looks like a `:stay' -- Eglot passes no mode, only the region."
  (let* ((region (plist-get args :region))
         (stay (and region (eq (car region) (cdr region)))))
    (cond ((and stay (null diags)) nil)
          (stay (apply orig (append flycheck-eglot--diagnostics diags nil) args))
          (t (apply orig diags args)))))

(with-eval-after-load 'flycheck
  (advice-add 'flycheck-eglot--report :around
              #'my/flycheck-eglot-report-honour-stay))
#+end_src

One gap is left, and it is a timing one. Roslyn loads the workspace in the
background, and the first pull races it: connecting to a one-project solution
gave =items: []= a second before =Successfully completed load of ...=. Nothing
re-checks when the load finishes -- Roslyn does not push, and Flycheck only
re-runs on its own triggers -- so the buffer stays empty until you type or save.
On a real solution that window is minutes, which reads exactly like "no errors".

Roslyn does announce it, with a =workspace/projectInitializationComplete=
notification. Unlike the two fixes above this needs no advice on a private
function: =eglot-handle-notification= is a public generic whose catch-all method
ignores anything unrecognised, so adding a method is purely additive.

#+begin_src emacs-lisp
(defun my/eglot-recheck-managed-buffers (server)
  "Re-run Flycheck in every buffer SERVER manages.

** File-watch globs

Eglot's glob grammar leaves the comma out of its literal character class:

#+begin_example
(:literal "[^][,*?{}]+" eglot--glob-emit-self)
#+end_example

A comma is only special inside brace expansion (={a,b}=), so a filename that
contains one cannot be parsed at all. Roslyn asks Eglot to watch the
MSBuild-generated =obj/.../.NETCoreApp,Version=v10.0.AssemblyAttributes.cs=, and
every connect then reports:

#+begin_example
Error running timer: (error "Glob '.NETCoreApp,Version=v10.0.…' invalid at 12")
#+end_example

The damage is a little wider than one skipped file. =eglot--glob-compile= parses
eagerly, before its own =NOERROR= argument can apply -- =NOERROR= only wraps the
/generated/ matcher, not the parse. So the error escapes the =mapc= inside the
=workspace/didChangeWatchedFiles= registration, and the =maphash= that actually
creates the watches runs /after/ that =mapc=. Every glob in the *same
registration* is therefore lost, not just the bad one. Roslyn sends several
registrations, so the rest survive: measured on a one-project solution, 137
watches without this advice and 140 with it.

Making a single unparseable glob skip itself keeps its registration. That is the
right outcome here -- the file in question is a generated build artefact nobody
watches deliberately -- and it covers any future glob Eglot cannot read, not just
commas. It also silences an error on every connect.

#+begin_src emacs-lisp
(defun my/eglot-glob-compile-tolerantly (orig glob &optional byte-compile noerror)
  "Skip a watch GLOB that will not compile, rather than abort the batch.
ORIG is `eglot--glob-compile', whose NOERROR only guards the matcher it builds,
not the parse that builds it.  Returns a matcher that matches nothing, in the
same shape ORIG would have returned for BYTE-COMPILE."
  (condition-case err
      (funcall orig glob byte-compile noerror)
    (error
     (message "eglot: skipping unwatchable glob %s: %s"
              glob (error-message-string err))
     (let ((form '(lambda (_string) nil)))
       (if byte-compile (byte-compile form) form)))))

(with-eval-after-load 'eglot
  (advice-add 'eglot--glob-compile :around #'my/eglot-glob-compile-tolerantly))
#+end_src

** ESLint

ESLint runs as a language server, behind the [[*Eglot][=rass= multiplexer]]. It
used to be [[*Diagnostics (Flycheck)][Flycheck]]'s =javascript-eslint= checker,
which shells out to =eslint --format=json --stdin=. A type-aware
=typescript-eslint= configuration makes each run take about six seconds, and
Flycheck starts a check on =idle-change= and on =new-line= by default. Flycheck
cancelled each slow run and started it again, so few runs ever finished. The
language server keeps one warm process instead.

The checker stays registered, and it is still the checker in a buffer without a
connection. Eglot is started by hand, and the =eglot-check= predicate requires
=eglot-managed-p=, so Flycheck falls through to =javascript-eslint= whenever no
server is attached. That path keeps the six-second cost, so the TS mode hooks
limit =flycheck-check-syntax-automatically= to =save= alone. =mode-enabled= is
excluded on purpose: [[*Consult][Consult]] previews a file candidate by opening
it, which would put a six-second run behind every TS file scrolled past. The
limit cannot delay LSP diagnostics: =flycheck-eglot--report= calls
=flycheck-buffer-automatically= with no condition, and
=flycheck-may-check-automatically= returns non-nil for any trigger list.

Either way the results land in Flycheck, fixes included. Flycheck 38 parses
ESLint's own suggested fixes from the CLI, and converts LSP quickfix code actions
into the same kind of fix (=flycheck-eglot-code-actions=, on by default). So
=C-c ! f= applies one at point and =C-c ! F= applies every fixable finding in the
buffer as a single undo step, from whichever side supplied it.

#+begin_src emacs-lisp
;; The fallback CLI checker costs ~6s per run, so do not start one while typing,
;; and do not start one when the buffer opens either -- Consult previews a file
;; candidate by opening it, so `mode-enabled' put a 6s run behind every TS file
;; scrolled past. Buffer-local on purpose: the Nix and Elisp checkers are fast,
;; and live results are worth having there.
(defun my/eslint-limit-check-triggers ()
  "Check on save only, so the slow ESLint CLI fallback does not thrash."
  (setq-local flycheck-check-syntax-automatically '(save)))

(dolist (hook '(tsx-ts-mode-hook typescript-ts-mode-hook js-ts-mode-hook))
  (add-hook hook #'my/eslint-limit-check-triggers))
#+end_src

** Opening a pull request

=my/browse-pull-request= (=<leader> g p=) takes the current branch straight to
GitHub's "compare" view (=/pull/new/<branch>=), which offers to open a PR
against the repository's default branch -- no need to switch to a browser tab
and find the branch by hand. It shells out to =git= via Magit's own
=magit-git-string=/=magit-get-current-branch= (autoloaded, so this does not
force Magit to load until actually called) rather than adding a dependency on
=forge= or the =gh= CLI, neither of which config.org otherwise needs.

The =origin= remote is read whether it is the SSH or HTTPS form
(=git@github.com:owner/repo.git= or =https://github.com/owner/repo.git=); a
non-GitHub =origin= (a different forge, or none at all) is reported with
=user-error= rather than silently opening a wrong URL.

#+begin_src emacs-lisp
(defun my/browse-pull-request ()
  "Open a new pull request for the current branch on GitHub.
Reads the `origin' remote and the current branch from Magit, and opens
GitHub's compare view for that branch, which offers to open a PR against the
repository's default branch."
  (interactive)
  (let* ((remote (magit-git-string "remote" "get-url" "origin"))
         (branch (magit-get-current-branch)))
    (unless remote
      (user-error "No `origin' remote configured"))
    (unless branch
      (user-error "Not on a branch"))
    (unless (string-match "github\\.com[:/]\\(.+?\\)\\(\\.git\\)?\\'" remote)
      (user-error "`origin' is not a GitHub remote: %s" remote))
    (browse-url (format "https://github.com/%s/pull/new/%s"
                        (match-string 1 remote) branch))))
#+end_src

* JavaScript/TypeScript

The =add-node-modules-path= package defaults to running =npm bin= to locate the
directory, but that command was removed in npm v9, so it silently does nothing
on a modern toolchain. Instead, locate the nearest =node_modules/.bin= with
=locate-dominating-file= and prepend it to a buffer-local =exec-path= / =PATH=.
This is package-manager agnostic (npm/pnpm/yarn) and spawns no subprocess, and
runs on the mode hook so the project-local servers are already on =exec-path= and
PATH before a manually-started =M-x eglot= spawns =rass=. =rass= inherits that
PATH and resolves each server itself, so the project's own
=typescript-language-server= and =eslint= win over the ones in the Nix closure.

#+begin_src emacs-lisp
(defun my/add-node-modules-path ()
  "Prepend the nearest node_modules/.bin to a buffer-local `exec-path'.
Replaces `add-node-modules-path', whose `npm bin' default was removed in npm 9."
  (when-let* ((root (locate-dominating-file default-directory "node_modules"))
              (bin  (expand-file-name "node_modules/.bin" root)))
    (when (file-directory-p bin)
      (setq-local exec-path (cons bin exec-path))
      (setq-local process-environment
                  (cons (concat "PATH=" bin path-separator (getenv "PATH"))
                        process-environment)))))

;; `js-ts-mode-hook' as well as `js-mode-hook': `treesit-auto-add-to-auto-mode-alist'
;; is called with `all', so a .js file opens in `js-ts-mode', and Emacs does not

;; relation only drives `:modes' matching -- not hooks. `js-mode-hook' stays for

;; is absent.
(dolist (hook '(tsx-ts-mode-hook typescript-ts-mode-hook

* AI agents

[[https://github.com/xenodium/agent-shell][=agent-shell=]] is an Emacs frontend for coding agents that speak the Agent
Client Protocol (ACP). It shells out to an external agent process per session;
=acp= and =shell-maker= (its ELisp dependencies) come from Nix alongside it.
agent-shell ships seventeen backends; two are wired here:

- Copilot via =agent-shell-github-start-copilot=, which runs =copilot --acp=
  (the default of =agent-shell-github-acp-command=).
- Claude Code via =agent-shell-anthropic-start-claude-code=, which runs
  =claude-agent-acp= (the default of =agent-shell-anthropic-claude-acp-command=).
  This is the =@agentclientprotocol/claude-agent-acp= adapter: it drives the
  Claude Agent SDK, which in turn shells out to an actual =claude= executable --
  nixpkgs' own build of it, by default, referenced via a =CLAUDE_CODE_EXECUTABLE=
  env var that =wrapProgram= bakes into =claude-agent-acp= at build time (an
  absolute store path, not a =PATH= lookup). =claude-agent-acp= is unfree only
  because nixpkgs builds it against that =claude-code= package, hence the added
  =config.allowUnfreePredicate= entry in [[file:flake.nix][=flake.nix=]].

  The home-manager profile installs its own, separately-updated =claude= (via
  =sadjow/claude-code-nix=), so =CLAUDE_CODE_EXECUTABLE= is overridden below to
  point at whichever =claude= resolves on =PATH= at the time =agent-shell= loads,
  rather than nixpkgs' bundled build -- one Claude Code binary, kept current in
  one place, instead of two independent copies drifting apart.

The Google backend is deliberately unwired. Antigravity is what Google is
migrating Gemini CLI's users to, but agent-shell has no dedicated Antigravity
backend yet, and Antigravity CLI (=agy=) has no ACP support to wire against --
confirmed directly: neither =agy --help= nor a =strings= scan of the binary
shows an ACP flag or library reference (Antigravity CLI 1.1.13), and
=agy --acp= itself just errors with "flags provided but not defined". A
bound-but-broken start command is worse than an absent one. Revisit once
Google ships ACP support.

The =copilot= and =claude-agent-acp= binaries are on =PATH= via the Nix tool
closure (=emacsToolsFor= in [[file:flake.nix][=flake.nix=]]), so both command
defaults resolve without further configuration. Authentication is handled by
each CLI/adapter itself (login/subscription or API-key env var via the
backend's =…-authentication= / =…-environment= defcustoms), so no secrets live
here. There is no keybinding; launch with =M-x agent-shell= (pick a backend) or
=agent-shell-github-start-copilot= / =agent-shell-anthropic-start-claude-code=
directly.

#+begin_src emacs-lisp
(use-package agent-shell
  :defer t
  :commands (agent-shell
             agent-shell-github-start-copilot
             agent-shell-anthropic-start-claude-code)
  :config
  ;; Prefer the home-manager-managed `claude' on PATH over nixpkgs' own
  ;; `claude-code' build that `claude-agent-acp' defaults to. `executable-find'
  ;; runs once here, at load time (agent-shell is `:defer'red, so this is well
  ;; after `exec-path-from-shell' has imported the shell PATH) -- if no `claude'
  ;; is found, `agent-shell-anthropic-claude-environment' is left at its default
  ;; and `claude-agent-acp' falls back to the store path it was built with.
  (when-let* ((claude (executable-find "claude")))
    (setopt agent-shell-anthropic-claude-environment
            (agent-shell-make-environment-variables
             "CLAUDE_CODE_EXECUTABLE" claude))))
#+end_src
